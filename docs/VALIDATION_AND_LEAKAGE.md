# 验证设计与数据泄漏

先回答：预测什么、什么时候预测、到那一刻哪些字段已经可用、验证需要模拟什么场景？

| 场景 | 划分 | 常见错误 |
|---|---|---|
| 近似独立样本 | KFold / train_test_split | 无意用全部数据预处理 |
| 分类比例差异 | StratifiedKFold | 只看 accuracy |
| 同一客户/患者多行 | GroupKFold | 同一个体出现在两边 |
| 过去预测未来 | 按时间 / TimeSeriesSplit | 随机打乱时序 |
| 每个时间戳有多个标的 | 按唯一时间戳划分 | 同一时刻的不同标的跨两边 |
| 未来一段时间的收益或波动率 | 时间划分 + purge/gap | 相邻标签覆盖相同未来区间 |

## 训练内拟合

中位数、标准化、PCA、词表、特征选择、缺失率驱动的删列、目标编码、截尾分位点，都属于需要学习的步骤。
把它们放进 Pipeline；交叉验证应传入整个 Pipeline。
确定性的逐行规则（例如面积相加）可直接应用，但数据可用时间仍必须正确。

## 三层使用

1. 开发训练：拟合模型。
2. 开发 CV：选模型、调参数、分析错误。
3. 预留集：方案确定后检查一次。

反复查看并据此修改后，预留集也变成了开发信息。需要新的独立证据，或嵌套交叉验证。
排行榜也不能替代本地验证；反复按公开榜单挑模型会过拟合榜单。

## OOF 与融合

OOF（out-of-fold）预测必须来自没训练过该行的模型。
Stacking 的第二层只用第一层 OOF 训练，不能用第一层对自身训练数据的拟合值。
融合权重用开发 CV 选择，不能在最终预留标签上搜索。

## 时间特征

- 一步滚动预测可以用前一天已经发布的真实值。
- 一次性预测未来 30 天，不能用第 2～30 天尚未知的真实目标构造 lag。
- 数据库中的更新后字段不一定在历史预测时点已存在；考虑 point-in-time join。
- 分组标签与时间同时存在时，先明确要预测新客户还是已有客户的未来；两种任务划分不同。
